# MaxBot

SaaS-сервис для мессенджера [MAX](https://max.ru). Дублирует посты канала в группу обсуждений, управляет верификацией новых участников (captcha-gate), отвечает в личных сообщениях через AI-ассистента, ведёт инбокс переписок и публикует отложенные посты.

Один экземпляр сервиса обслуживает **множество пользователей и ботов**: каждый пользователь добавляет свои MAX-токены через веб-интерфейс, токены шифруются Fernet'ом и хранятся в PostgreSQL.

## Возможности

### Канал → группа обсуждений
- **Автодублирование постов** — бот отслеживает новые публикации в канале и пересылает их в группу обсуждений с шапкой-ссылкой на источник.
- **Кнопка комментариев** — к каждому посту в канале прикрепляется inline-кнопка «💬 Прокомментировать», ведущая прямо в обсуждение.
- **Дедупликация** — повторные `message_created` (которые присылает MAX при сетевых сбоях) игнорируются по таблице `PostLink`.

### Верификация участников (captcha-gate)
- **Автоматическое приветствие** — при вступлении нового участника бот шлёт в группу сообщение с deep-link кнопкой подтверждения.
- **Read-only до верификации** — поскольку MAX API не поддерживает mute/restrict, сообщения непроверенного участника удаляются (см. `bot/handlers.py:_delete_if_unverified`).
- **Кик по таймауту** — `scheduler` каждые 60 сек проверяет просроченные запросы и при необходимости исключает участника.
- **Welcome-DM** — после верификации бот шлёт пользователю личное сообщение с кнопкой «Вернуться в группу».
- **Гибкие шаблоны** — поддерживаются плейсхолдеры `{имя}`, `{группа}`, `{минут}`. Дефолтные шаблоны вынесены в [bot/constants.py](bot/constants.py).
- **Два режима конфигурации:**
  - **Самостоятельные конфиги** (`WelcomeConfig`) — рекомендуемый путь: верификация для любой группы без привязки к каналу.
  - **Пары канал → группа** — legacy-путь: верификация прямо в существующей паре. WelcomeConfig имеет приоритет.

### AI-ассистент в личных сообщениях
- **OpenAI-совместимое API** — поддерживается OpenRouter (по умолчанию), Ollama, OpenAI и любые провайдеры с `/chat/completions`.
- **Per-(bot, group) конфиги** — для каждой группы можно настроить отдельную модель, system-prompt и API-ключ.
- **Полная история переписки** — каждый user/assistant-обмен пишется в `ConversationMessage` и используется как контекст следующего ответа.
- **Связь по верификации** — после captcha-gate пользователь автоматически становится «членом» AI-комнаты (см. `UserBotContext`).
- **Шифрование ключей** — API-ключи AI хранятся Fernet'ом, как и токены ботов.

### Веб-инбокс
- **Просмотр переписок** — отдельная страница `/bots/{id}/inbox`: видно все DM с пользователями, фильтр по группе.
- **Счётчики непрочитанных** — `InboxReadStatus` помнит время последнего открытия; на аватарке группы и пользователя показывается badge.
- **Аватары** — иконки чатов и пользователей подтягиваются из MAX API параллельно (`asyncio.gather`) и кешируются в `ConversationMessage.user_avatar` для следующих запросов.
- **Ручной ответ** — владелец может ответить пользователю прямо из инбокса, ответ сохраняется как `role="assistant"` в той же переписке.

### Публикация
- **Автопостинг** — `scheduler` каждые 30 сек публикует отложенные посты; поддерживается Markdown и вложения.
- **Очередь постов** — статусы `pending → sent / failed` с сохранением текста ошибки.

### Управление
- **Multi-bot** — каждый пользователь добавляет несколько ботов и распределяет их по парам/конфигам.
- **Веб-интерфейс** — полный CRUD через FastAPI + Jinja2 + Tailwind.
- **Журнал событий** — `EventLog` с уровнями info/warning/error, привязанный к пользователю и боту.
- **Теплая замена токена** — при обновлении токена через UI он валидируется на стороне MAX API до сохранения, а супервайзер автоматически подхватит новый токен на следующей итерации.

## Архитектура

5 контейнеров в `docker-compose.yml` делятся на три слоя:

```
┌─────────────────────────────────────────────────────────────────┐
│                  PostgreSQL 16 (db)                              │
│      ── единственный источник истины для всего сервиса ──        │
└──────────────┬───────────────┬─────────────────┬────────────────┘
               │               │                 │
        ┌──────┴──────┐ ┌──────┴──────┐ ┌────────┴────────┐
        │     web     │ │    bot      │ │    scheduler    │
        │  (FastAPI)  │ │ (supervisor)│ │  (APScheduler)  │
        │             │ │             │ │                 │
        │ HTML + REST │ │ long-polling│ │ автопостинг     │
        │ /api/*      │ │ + handlers  │ │ + кик по таймауту│
        │ /api/webhook│ │             │ │                 │
        └─────────────┘ └─────────────┘ └─────────────────┘
                ▲              │                 │
                │              ▼                 ▼
                │        ┌───────────────────────────┐
                │        │       MAX Bot API          │
                │        │   platform-api.max.ru      │
                └────────┴───────────────────────────┘
```

И отдельный сервис `migrate` — выполняется один раз перед стартом остальных, прогоняет `alembic upgrade head`.

### Поток обработки события (polling-режим)
```
MAX API → bot.client.MaxClient.get_updates(marker)
       → bot.supervisor._poll_loop
       → bot.handlers.handle_update(update)
       → один из:
            _handle_message_created  ── дублирование канал→группа / DM в AI / удаление до верификации
            _handle_member_added     ── создание VerificationRequest
            _handle_bot_started      ── обработка deep-link verify_<token>
       → коммит в БД
       → сохранение нового marker
```

### Поток отложенной публикации
```
APScheduler (каждые 30 сек)
       → scheduler.publish_due_posts
       → SELECT pending posts WHERE scheduled_at <= now()
       → для каждого:
            decrypt_token(bot.encrypted_token)
            client.send_message(channel)
            client.send_message(group)  ── дубликат
            INSERT PostLink + EventLog
            UPDATE post.status = sent | failed
```

### Поток верификации
```
1. user_added           → handler создаёт VerificationRequest(pending)
                       → шлёт в группу сообщение с deep-link
2. /start verify_<tok>  → handler проверяет deadline и токен
                       → status = verified
                       → удаляет приветствие в группе
                       → шлёт welcome-DM
3. таймаут истёк        → scheduler.kick_expired_verifications
                       → kick_member (если включено)
                       → удаляет приветствие
                       → status = kicked
```

## Быстрый старт

### Требования
- Docker и Docker Compose

### Запуск

```bash
git clone https://github.com/ProKoKos/maxbot.git
cd maxbot
cp .env.example .env
```

Заполните `.env` минимум:

```env
SECRET_KEY=<случайная строка 32+ символов>
ENCRYPTION_KEY=<Fernet-ключ, см. ниже>
ADMIN_EMAIL=you@example.com
ADMIN_PASSWORD=yourpassword
POSTGRES_PASSWORD=yourdbpassword
```

Сгенерировать `ENCRYPTION_KEY`:
```bash
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
```

Запустить:
```bash
make up
# либо вручную:
docker compose up --build -d
```

Откройте [http://localhost:8000](http://localhost:8000) и войдите данными из `.env`.

> **Внимание:** при добавлении новой миграции пересобирайте сервис `migrate` вместе с остальными — он отдельный образ (см. `CLAUDE.md`).

## Настройка

### 1. Добавить бота
**Боты** → **+ Добавить бота**. Введите токен MAX-бота (получить у [@MaxBot](https://max.ru/maxbot)). Токен валидируется через MAX API и шифруется Fernet'ом перед сохранением.

> Бот должен быть **администратором** в канале и **участником** группы обсуждений.

### 2. Создать пару канал → группа
**Пары** → **+ Добавить пару**. После выбора бота список каналов и групп подгружается из MAX API. Ссылка на группу подставляется автоматически по правилу: MAX API → `ChannelGroupPair.group_link` → ручной ввод (см. `CLAUDE.md`).

### 3. Настроить верификацию
**Вариант А** — внутри пары: на странице **Пары** включите «Верификация» в настройках конкретной пары.

**Вариант Б (рекомендуется)** — самостоятельный конфиг: **Верификация** → **+ Добавить группу**. Бот будет встречать новых участников в любой группе, где состоит, без необходимости заводить пару с каналом.

При вступлении нового пользователя:
1. Бот шлёт в группу сообщение с deep-link кнопкой.
2. Сообщения пользователя автоматически удаляются до верификации.
3. Пользователь открывает бота, нажимает «Я не бот» → проверка пройдена.
4. Бот удаляет сообщение из группы и шлёт welcome-DM.
5. Если таймаут истёк, scheduler исключает пользователя (если включён кик).

### 4. AI-ассистент
**Ассистент** → **+ Добавить группу**. Укажите бота, group_id, system-prompt, модель и API-ключ (по умолчанию OpenRouter, можно переопределить URL).

После верификации в этой группе пользователь становится «членом» AI-комнаты — все его DM в боте обрабатываются ассистентом, переписка сохраняется в `ConversationMessage`.

### 5. Инбокс
**Боты** → откройте конкретного бота → **Инбокс**. Видно все переписки бота с пользователями, фильтр по группе. Можно ответить вручную — ответ уйдёт в DM и сохранится в истории как сообщение от ассистента.

### 6. Автопостинг
**Автопостинг** → создайте отложенный пост: пара, текст (Markdown), время. `scheduler` опрашивает очередь каждые 30 сек.

## Модели базы данных

| Модель                | Назначение                                                      |
|-----------------------|-----------------------------------------------------------------|
| `User`                | Пользователь сервиса                                            |
| `Subscription`        | Тарифный план и лимиты (хранятся как JSON)                      |

| `EventLog`            | Журнал событий (`info`/`warning`/`error`)                       |
| `AssistantConfig`     | Per-(bot, group) конфиг AI-ассистента; `api_key` зашифрован     |
| `UserBotContext`      | «Членство» MAX-пользователя в AI-комнате                        |
| `ConversationMessage` | История переписки для контекста модели и инбокса                |
| `InboxReadStatus`     | Время последнего открытия переписки (для счётчиков непрочитанных)|

## Известные ограничения

Эти ограничения сейчас приемлемы для масштаба сервиса, но стоит держать их в голове при планировании развития:

- **Нет distributed lock в scheduler** — при горизонтальном масштабировании (≥ 2 экземпляров `scheduler`) джобы могут продублировать публикации. Решение: pg_advisory_lock или Celery beat.
- **In-memory rate-limiter** — лимиты сбрасываются при рестарте процесса и не разделяются между worker'ами Uvicorn. Решение: Redis-backed sliding window.
- **Нет CSRF-защиты на форме `/login`** — компенсируется `samesite=lax` cookie. Для production-нагрузки желательно добавить CSRF-токен.
- **Нет автоматических тестов** — критические потоки (handlers, scheduler) сейчас покрываются только ручным тестированием.
- **Race condition в `_handle_bot_started`** — если пользователь дважды быстро нажмёт кнопку, второй вызов вернёт «Вы уже прошли верификацию», но никаких побочных эффектов не будет. Если же критично, можно добавить `SELECT … FOR UPDATE`.
- **MAX API не поддерживает mute/restrict** — read-only до верификации реализовано через удаление сообщений (см. `bot/handlers.py:_delete_if_unverified`).
